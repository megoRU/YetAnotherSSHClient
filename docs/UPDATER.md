# Автообновление Tauri

Документ описывает, как устроено автообновление в сборке на Tauri 2 и почему
оно не может сломать запуск приложения.

## 1. Схема целиком

```
┌─────────────────────────┐        1. GET latest.json        ┌──────────────────────────┐
│ Приложение (клиент)     │ ──────────────────────────────▶ │ raw.githubusercontent.com │
│ src-tauri/src/updates.rs│ ◀────────────────────────────── │ src-tauri/updater/       │
│                         │        2. version > current?     │ latest.json (в ветке)    │
│                         │                                 └──────────────────────────┘
│                         │        3. Скачивание артефакта             │
│                         │ ◀──────────────────────────────────────────┘
│                         │        4. Проверка подписи minisign
│                         │        5. Установка (NSIS / .app / AppImage)
│                         │        6. Перезапуск
└─────────────────────────┘
```

Клиентская часть — `src-tauri/src/updates.rs` и плагин
`tauri-plugin-updater`. Манифесты — статические файлы
`src-tauri/updater/latest.json` (стабильный канал) и
`src-tauri/updater/prerelease.json` (канал pre-release), которые лежат в
репозитории и обновляются CI. Какой из них опрашивается, решает настройка
«Получать обновления Pre-release» — см. раздел 3.3.

## 2. Подпись обновлений

Tauri updater v2 использует формат **minisign**.

1. Ключи создаются один раз и хранятся в менеджере паролей мейнтейнера:

   ```bash
   npx tauri signer generate -w ~/.tauri/yassh.key
   ```

2. Секреты в репозитории (GitHub → Settings → Secrets and variables):
   * `TAURI_SIGNING_PRIVATE_KEY` — содержимое приватного ключа ( multiline);
   * `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` — пароль приватного ключа.

3. Переменная репозитория (не секрет) `TAURI_UPDATER_PUBLIC_KEY` — публичный
   ключ **в том же виде, что и в конфиге**: base64 от всего файла `.pub`,
   который декодируется в `untrusted comment: minisign public key: <ID>\nRWQ…`.
   Именно base64, а не «голый» ключ, и не текст с переводом строки.

   Проверка в `gen-updater-config.mjs` принимает оба формата — base64 от файла
   и «голый» 32-байтный ключ `RWQ…`, потому что Tauri понимает оба, а
   `plugins.updater.pubkey` в `tauri.conf.json` содержит первый.

   Он публичный, но хранится в переменной, чтобы не коммитить его в конфиг до
   момента готовности.

4. `scripts/gen-updater-config.mjs` (запускается в CI) генерирует
   `src-tauri/tauri.updater.generated.json`:

   * `TAURI_UPDATER_ENABLED` не `true` или ключа нет ⇒
     `bundle.createUpdaterArtifacts: false`, сборка идёт без подписи;
   * иначе подставляется `pubkey` и запрашиваются артефакты обновления;
   * если приватный ключ не задан при включённом обновлении, CI падает **до**
     сборки: иначе вышел бы релиз, который приложение не способно проверить.

Файл генерируется в `src-tauri/`, добавлен в `.gitignore` и никогда не
коммитится: секреты не покидают CI.

## 3. Endpoint и манифест

`tauri.conf.json`:

```jsonc
"updater": {
  "pubkey": "REPLACE_WITH_TAURI_UPDATER_PUBLIC_KEY_PLACEHOLDER",
  "endpoints": [
    "https://raw.githubusercontent.com/megoRU/YetAnotherSSHClient/main/src-tauri/updater/latest.json"
  ],
  "prereleaseEndpoints": [
    "https://raw.githubusercontent.com/megoRU/YetAnotherSSHClient/main/src-tauri/updater/prerelease.json"
  ],
  "windows": { "installMode": "passive" }
}
```

`src-tauri/updater/latest.json` — безопасное значение по умолчанию:

```json
{ "version": "0.0.0", "notes": "…", "pub_date": "1970-01-01T00:00:00Z", "platforms": {} }
```

Версия `0.0.0` ниже любой собранной версии, а пустой `platforms` означает, что
предлагать нечего: приложение показывает «обновлений нет» и ничего не меняет.
Это состояние по умолчанию, а не ошибка конфигурации.

Плагин ищет платформу в `platforms` **до** сравнения версий, поэтому пустой
объект даёт ошибку `TargetNotFound`/`TargetsNotFound`. `updates.rs` распознаёт
её через `is_no_update_error()` и возвращает `Ok(None)`, то есть
`not-available`, а не `error`: пользователю не о чем сообщать, когда
скачивать нечего.

### 3.1. Генерация манифеста в CI

Сборка идёт в матрице, и на каждой платформе известны только её артефакты.
Поэтому генерация разбита на два шага — иначе последняя matrix-платформа
затёрла бы остальные, и в манифесте остался бы один target:

| Шаг                         | Где                        | Что делает                                                                                       |
|-----------------------------|----------------------------|--------------------------------------------------------------------------------------------------|
| `gen-updater-manifest.mjs fragment` | каждая платформа матрицы | сканирует свой каталог бандла, находит подпись своей платформы и пишет `updater/fragments/fragment-<platform>.json` |
| `gen-updater-manifest.mjs merge`     | отдельный job `updater-manifest` | скачивает все фрагменты в `updater/fragments/`, объединяет в `prerelease.json` и — только для стабильной версии — в `latest.json`, коммитит один раз |

Сопоставление подписей с платформами Tauri: `windows-x86_64`,
`darwin-aarch64`, `darwin-x86_64`, `linux-x86_64`, `linux-aarch64`. Скрипт
падает, если фрагменты собраны для разных версий/тегов или если платформа
попала в манифест дважды; отсутствующие платформы перечисляются в логе.
Если подписанных артефактов нет вовсе — остаётся безопасный нулевой манифест.

**Пре-релизная сборка (`4.1.0-rc.1`) обновляет только `prerelease.json`.**
`latest.json` продолжает указывать на последний стабильный релиз — иначе rc
достался бы всем пользователям, включая тех, кто pre-release отключил.

#### Имена подписываемых файлов (Tauri 2)

Tauri 2 подписывает **сам бандл**, а не отдельный updater-архив: `tauri-cli`
берёт пакеты `Updater | Nsis | WindowsMsi | AppImage | Deb | Rpm`, а
`tauri-bundler` создаёт `PackageType::Updater` (zip/tar.gz) только если среди
целей есть `.app`. Отсюда имена, которые ищет `detectPlatform`:

| Платформа | Подписанный файл | Артефакт обновления в релизе |
|---|---|---|
| Windows | `YASSH Client_4.0.0_x64-setup.exe` | `.exe` (NSIS-установщик) |
| macOS | `YASSH Client.app.tar.gz` | `.app.tar.gz` |
| Linux | `YASSH Client_4.0.0_amd64.AppImage` | `.AppImage` |

`.nsis.zip` в Tauri 2 не создаётся, поэтому Windows обновляется запуском самого
NSIS-установщика. Токен архитектуры есть только в имени AppImage, так что для
macOS платформа берётся из `TAURI_UPDATER_PLATFORM`: по имени `arm64` и `x64`
не различить.

Промежуточные файлы `fragment-*.json` и каталог `fragments/` добавлены в
`.gitignore`: в git попадают только собранные манифесты.

### 3.2. Тег релиза и URL артефактов

URL в манифесте строится как
`https://github.com/<repo>/releases/download/<tag>/<файл>`, поэтому тег обязан
совпадать с фактическим тегом GitHub Release — иначе ссылки не резолвятся и
обновление не скачивается.

Тег равен версии **без** префикса `v`: для `4.0.0` это тег `4.0.0`, и его же
создаёт `draft-release` в workflow. Скрипт проверяет согласованность
(`TAURI_UPDATER_VERSION` / `TAURI_UPDATER_TAG`) и останавливает сборку при
расхождении.

### 3.3. Каналы: стабильный и pre-release

Плагин `tauri-plugin-updater` **не умеет** отсекать пре-релизы: он берёт
первый ответивший endpoint и предлагает его версию, если она новее текущей.
Поэтому каналов два, и это два разных манифеста:

| Настройка «Получать обновления Pre-release» | Опрашиваемый манифест | Что предлагается |
|---|---|---|
| выключена (по умолчанию) | `latest.json` (`endpoints`) | только стабильные релизы |
| включена | `prerelease.json` (`prereleaseEndpoints`) | стабильные релизы **и** rc/beta/alpha |

Оба списка лежат в `plugins.updater`, но в списке `endpoints` находится
**только** стабильный канал: иначе плагин, перебрав endpoint'ы по порядку,
отдал бы пользователю `prerelease.json` независимо от настройки. Выбором канала
занимается `updates::endpoint(app, allow_pre_release)`, а он дополнительно
сверяется:

* при поиске обновления (`fetch_update`) пре-релиз из манифеста отбрасывается,
  если настройка выключена;
* перед установкой (`start_download`) — на случай, если пользователь выключил
  настройку уже после того, как обновление нашлось.

Обе проверки используют `updates::is_pre_release()` (префикс `-rc.1`, `-beta` в
semver-версии).

**Неопубликованный манифест pre-release — не ошибка.** Пока `prerelease.json`
не закоммичен в ветку, адрес отдаёт `404`, а плагин превращает это в
`ReleaseNotFound` («Could not fetch a valid release JSON from the remote»).
Поэтому ошибки классифицируются (`classify_error`): `ReleaseNotFound` в
канале pre-release приводит к откату на стабильный канал, а не к сообщению
об ошибке — канал необязателен, и его отсутствие не должно пугать
пользователя. Ошибки стабильного канала по-прежнему показываются как раньше.

Чтобы канал работал без fallback, `src-tauri/updater/prerelease.json` должен
лежать в ветке: он попадает туда сам — коммитом или следующим прогоном CI
(шаг `merge` пишет оба манифеста).

Для локальной проверки каналов есть переменные окружения
`YASSH_UPDATER_ENDPOINT` (стабильный) и `YASSH_UPDATER_PRERELEASE_ENDPOINT`
(pre-release): непустое значение заменяет endpoint из конфига. В production они
не выставляются.

Настройка хранится в `AppConfig.allowPreReleaseUpdates`
(`allow_pre_release_updates` в Rust), то есть переносится вместе с бэкапом
настроек.

## 4. Проверка и установка

Порядок в `src-tauri/src/updates.rs`:

1. `check()` отдаёт `update-status: checking`.
2. Если публичный ключ не настроен (placeholder) — `not-available` и выход.
   Обновление **выключено целиком**, а не «падает при проверке подписи».
3. Выбирается канал по `allow_pre_release`: стабильный или pre-release
   (раздел 3.3).
4. `check()` у плагина: скачивание манифеста, выбор версии, проверка подписи
   манифеста.
5. Версия предлагается, только если `update.version > CURRENT_VERSION`
   (сравнение semver в `is_newer_version`). Откат запрещён.
6. Если канал pre-release выключен, версия-пре-релиз отбрасывается
   (`is_pre_release`), а перед установкой проверяется ещё раз.
7. Отклонённая пользователем версия запоминается в `AppConfig.updater`
   и больше не предлагается — в том числе после перезапуска приложения.
8. `update-available` уходит в UI **один раз** на версию; отметка
   `notifiedVersion` лежит в том же блоке конфига, поэтому перезапуск не
   приводит к повторному уведомлению.
9. Установка происходит только по явному действию пользователя
   (`start-update-download` → `quit-and-install`); автоустановки нет.
10. `app.restart()` вызывается исключительно после успешной установки.

## 5. Почему обновление не может сломать запуск

| Риск                                     | Защита                                                                                                       |
|------------------------------------------|--------------------------------------------------------------------------------------------------------------|
| Подменённый артефакт                     | minisign-подпись проверяется до установки; неподписанный файл не может заменить приложение                   |
| Неверный/отсутствующий ключ подписи      | Обновление выключено (`is_updater_configured()`); приложение работает на текущей версии                      |
| Откат на старую версию                   | Строгое `version > current`, `bundle.allowDowngrades` не используется                                        |
| Повторное предложение отклонённой версии | `skippedVersion` в `AppConfig.updater`                                                                         |
| «Обновление той же версии»               | Сравнение версий строгое, равные версии не предлагаются                                                      |
| Битый манифест / сеть недоступна         | Ошибка превращается в `update-error` + `update-status: error`; установленное приложение не трогается         |
| Манифест без артефакта этой ОС          | `TargetNotFound`/`TargetsNotFound` распознаются как «обновлений нет» (`is_no_update_error`), не как ошибка |
| Артефакт скачался, но подпись не совпала | `download_and_install` возвращает ошибку **до** замены файлов; UI показывает ошибку, версия остаётся прежней |
| Сбой при установке на Windows            | NSIS `installMode: passive` — установщик не требует подтверждений; при ошибке остаётся прежняя копия         |
| Повреждённый конфиг                      | `read_state()` при ошибке возвращает значения по умолчанию, а не паникует                                    |
| Импорт чужого бэкапа настроек            | Состояние обновлений — часть `AppConfig.updater`, поэтому переносится вместе с бэкапом                      |

### 5.1 Где лежит состояние обновлений

Служебные метки (`lastCheck`, `lastDownload`, `lastInstall`, `skippedVersion`,
`notifiedVersion`) лежат в блоке `AppConfig.updater` основного конфига. Раньше
для них существовал отдельный `~/.minissh_updater.json`, из-за чего бэкап
настроек был неполным, а в домашнем каталоге лежал лишний файл.

При первом запуске со сборкой, где блока ещё нет, `migrate_updater_state()`
переносит значения из старого файла в конфиг и **удаляет файл**. Миграция идёт
один раз; уже сохранённые в конфиге значения не затираются, а повреждённый файл
просто удаляется, не мешая запуску.

Отдельно: обновление **никогда** не удаляет пользовательские данные. Конфиг
лежит в `~/.minissh_config.json` и не входит в заменяемый набор файлов
приложения.

## 6. Проверка без публикации релиза

### 6.1. Чистая установка

1. Собрать приложение: `npm run build` (или взять артефакт из CI).
2. Установить в чистый профиль: отдельный каталог `HOME`/профиль Windows или
   отдельный пользователь Linux. Конфига `~/.minissh_config.json` быть не должно.
3. Запустить. Ожидается: мастер настройки хранилища, пустой список серверов.
4. Проверить `update-status`: `not-available` (ключ-заглушка) либо
   `available` с корректной версией, если обновление сконфигурировано.

### 6.2. Переход со старой версии

1. Установить Electron-сборку 3.2.2, добавить серверы и пароли, дождаться
   ввода ключа восстановления.
2. Закрыть приложение, установить Tauri-сборку поверх (тот же `appId`
   `com.yash.client`).
3. Запустить. Ожидается:
   * серверы, настройки и зашифрованные пароли на месте — формат
     `~/.minissh_config.json` не менялся;
   * `vault-get-status` возвращает `isInitialized: true`;
   * хранилище **не разблокировано автоматически**: `safeStorage` Electron
     недоступен Tauri, поэтому ключ вводится один раз. После этого ключ
     кладётся в системное хранилище (Windows Credential Manager / macOS
     Keychain / Linux Secret Service) и авторазблокировка работает как раньше.
4. Проверить `sftp-readdir` и `ssh-connect` на одном из сохранённых серверов.

### 6.3. Полный цикл обновления локально

Публиковать релиз для проверки не нужно: endpoint переопределяется
переменной окружения.

```bash
# 1. Собрать приложение с артефактами обновления (нужны ключи).
export TAURI_UPDATER_ENABLED=true
# Ровно то значение, что лежит в src-tauri/tauri.conf.json
# (plugins.updater.pubkey) — base64 от всего файла .pub.
export TAURI_UPDATER_PUBLIC_KEY="dW50cnVzdGVkIGNvbW1lbnQ6IG1pbmlzaWduIHB1YmxpYyBr…"
export TAURI_SIGNING_PRIVATE_KEY="$(cat ~/.tauri/yassh.key)"
export TAURI_SIGNING_PRIVATE_KEY_PASSWORD="…"
node scripts/gen-updater-config.mjs
npm run tauri -- build --config src-tauri/tauri.updater.generated.json

# 2. Собрать манифест из полученных артефактов (два шага, как в CI).
TAURI_UPDATER_VERSION=4.0.1 TAURI_UPDATER_TAG=4.0.1 \
  TAURI_UPDATER_PLATFORM=windows-x86_64 node scripts/gen-updater-manifest.mjs fragment
TAURI_UPDATER_VERSION=4.0.1 TAURI_UPDATER_TAG=4.0.1 \
  TAURI_UPDATER_FRAGMENTS=src-tauri/updater/fragments node scripts/gen-updater-manifest.mjs merge

# 3. Отдать манифест и артефакт по HTTP и указать приложению этот endpoint.
python -m http.server 8080
YASSH_UPDATER_ENDPOINT=http://127.0.0.1:8080/latest.json npm run dev

# 3.1. То же для канала pre-release: манифест prerelease.json и
#      переменная YASSH_UPDATER_PRERELEASE_ENDPOINT.
YASSH_UPDATER_PRERELEASE_ENDPOINT=http://127.0.0.1:8080/prerelease.json npm run dev
```

Дальше:

* в «Настройках → О программе» нажать «Проверить обновления» — должно
  появиться `available` с версией `4.0.1`;
* скачать обновление и нажать «Перезапустить и установить»: приложение
  перезапустится уже версией 4.0.1;
* после перезапуска проверка не должна предлагать обновление снова.

Переменные `YASSH_UPDATER_ENDPOINT` и `YASSH_UPDATER_PRERELEASE_ENDPOINT`
обрабатываются в `updates::endpoint()`: непустое значение заменяет endpoint
из конфига для своего канала. Это единственные намеренные «обходы»
конфигурации, и они существуют только для проверок — в production переменные не
выставляются.

### 6.4. Проверка переключателя Pre-release

1. Запустить приложение с `YASSH_UPDATER_ENDPOINT=…/latest.json`, где версия
   манифеста — `4.0.1-rc.1`, а с `YASSH_UPDATER_PRERELEASE_ENDPOINT=…/latest.json`
   — та же версия.
2. Оставить переключатель «Получать обновления Pre-release» выключенным и
   нажать «Проверить обновление»: обновления предлагаться не должны.
3. Включить переключатель: проверка повторяется автоматически и должна найти
   `4.0.1-rc.1`.
4. Выключить переключатель обратно и нажать «Установить обновление» на
   оставшейся карточке: установка обязана быть отклонена с понятным текстом,
   а версия — остаться прежней.

## 7. Включение автообновления

1. Создать ключи (`tauri signer generate`).
2. Сохранить приватный ключ и пароль в секретах репозитория.
3. Публичный ключ положить в переменную `TAURI_UPDATER_PUBLIC_KEY`.
4. Выставить `TAURI_UPDATER_ENABLED=true` в переменных репозитория.
5. Заменить placeholder в `src-tauri/tauri.conf.json` на реальный публичный
   ключ (или оставить placeholder и полагаться на подстановку из CI — но
   тогда локальный `npm run dev` не сможет проверить обновление; для
   локальной проверки используйте `YASSH_UPDATER_ENDPOINT` и подставьте ключ
   в сгенерированный конфиг).
6. Выполнить push в `main`: CI подпишет артефакты, обновит манифест и
   создаст **черновой** релиз.

Пока релиз остаётся черновиком, ссылки в манифесте недоступны для
публичного скачивания: загрузка вернёт 404 и обновление не установится —
приложение продолжит работать на текущей версии. Чтобы обновление заработало
для пользователей, релиз нужно один раз опубликовать.

## 8. Draft Release и публикация

Push **не публикует** релиз: `softprops/action-gh-release` вызывается с
`draft: true`. Черновик виден только мейнтейнерам; артефакты не попадают в
публичные релизы и не отображаются у пользователей.

Ручной запуск workflow с `inputs.publish: true` снимает флаг draft — это
единственный путь к публикации, и он требует явного действия.

Признак `prerelease` выводится из версии (`contains(version, '-')`): сборка
`4.0.1-rc.2` помечается как pre-release, стабильная `4.1.0` — нет. Это
независимо от ветки, из которой идёт сборка.
