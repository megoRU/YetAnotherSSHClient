# Инструкции для AI-агентов

Эти правила обязательны для всех AI-агентов, работающих с проектом.  
Если задача пользователя противоречит этим правилам, приоритет имеют эти инструкции, если пользователь явно не переопределил конкретное правило в текущей сессии.

---

## 1. Терминал (Terminal)

### `lineHeight`
- В `src/components/Terminal.tsx` параметр `lineHeight` **ВСЕГДА** должен иметь значение `1`.
- Запрещено устанавливать `1.1`, `1.2` или любое другое значение.
- Изменение разрешено **только если пользователь явно попросил изменить `lineHeight` в текущей сессии**.
- Не изменяй `lineHeight` косвенно через другие настройки или стили.

### Инициализация терминала
При инициализации терминала обязательно соблюдать правильный pipeline:

1. Создать и инициализировать терминал.
2. Подключить addons.
3. Выполнить `fitAddon.fit()`.
4. Только после этого устанавливать SSH-соединение.

`fitAddon.fit()` должен выполняться **до установки SSH-соединения**.

## 2. Стили и шрифты (Styles & Fonts)

### Пути к шрифтам
В CSS при использовании `@font-face`:

- Запрещено использовать пути с префиксом `./`.
- Использовать пути, начинающиеся непосредственно с директории.

Правильно:

`csssrc: url('/fonts/FontName.woff2');`

Запрещено:

`src: url('./fonts/FontName.woff2');`

Это необходимо для корректной работы ассетов в production-сборке Electron.

### Шрифты проекта

* **Никогда не удаляй файлы из `public/fonts/`.**
* **Никогда не удаляй существующие `@font-face`.**
* Все шрифты, перечисленные в `src/hooks/useSystemFonts.ts`, должны:

  * физически присутствовать в проекте;
  * быть зарегистрированы через `@font-face`;
  * корректно использоваться приложением.
* Не заменяй проектные шрифты системным fallback.
* Особенно важно не допускать fallback на `serif`.

### Иконки

* `./icons/icon48.png` в `TitleBar` должен сохранять существующий стиль.
* `./icons/icon256.png` в `SettingsView` должен сохранять существующий стиль.
* Не заменяй эти иконки без явного указания пользователя.
* Не изменяй их визуальный стиль в рамках рефакторинга или оптимизации.

## 3. Код и типизация (Code & Typing)

Проект использует строгую типизацию TypeScript.

### Запрещено

Без крайней необходимости запрещено использовать:

TypeScript: `any/unknown`

Предпочитай:

* конкретные типы;
* существующие типы проекта;
* generic-типы;
* type guards;
* discriminated unions.

Не ослабляй типизацию только для того, чтобы быстрее исправить ошибку компиляции.

### Важное правило

Не переписывай рабочую типизацию на `any` или `unknown` для устранения ошибок после рефакторинга.

## 5. Версионирование (Versioning)

Если пользователь **явно не указал версию**, которую необходимо установить:

* увеличивать версию только на `+0.0.1` за одну сессию.

Пример:

```text
1.8.1 → 1.8.2
```

После `.9` переносить разряд:

```text
1.8.9 → 1.9.0
1.9.9 → 2.0.0
```

При изменении версии обязательно синхронно обновлять **все шесть** мест:

| Файл                        | Что именно                                   |
|-----------------------------|----------------------------------------------|
| `package.json`              | `"version"`                                  |
| `package-lock.json`         | `"version"` в корне и в блоке `packages[""]` |
| `src/types.ts`              | `export const VERSION`                       |
| `src-tauri/Cargo.toml`      | `version` в `[package]`                      |
| `src-tauri/Cargo.lock`      | версия пакета `yassh-client`                 |
| `src-tauri/tauri.conf.json` | `"version"`                                  |

Два lock-файла обновляются инструментами, а не вручную — так меньше риск
оставить рассинхрон:

```bash
npm install --package-lock-only --ignore-scripts
cargo update -p yassh-client --manifest-path src-tauri/Cargo.toml
```

Остальные четыре правятся вручную. После правки обязательно проверь, что все
шесть совпадают, и что `tauri.conf.json` остался **без BOM**: `Set-Content`
в PowerShell с `-Encoding UTF8` добавляет BOM, после чего `tauri_build`
падает с «unable to parse JSON Tauri config file». Если BOM уже попал,
перезаписывай так:

```powershell
$text = [IO.File]::ReadAllText($path).TrimStart([char]0xFEFF)
[IO.File]::WriteAllText($path, $text, (New-Object System.Text.UTF8Encoding($false)))
```

Не изменяй версию в других файлах без необходимости: `README.md` и
документация версию не дублируют, упоминания версии в `.github/` и `docs/`
относятся к примерам, а не к актуальному значению.

### `releaseType`

В `package.json`:

`"releaseType": "draft"`

должно оставаться **всегда**.

Запрещено менять:

```text
draft → release
```

или на любое другое значение.

Не изменяй `releaseType`, даже если считаешь, что это необходимо для автообновлений или публикации.

## 7. Очистка временных файлов

После выполнения задачи удаляй генерируемый мусор, если он появился в результате работы агента.

В частности:

```text
tsconfig.node.tsbuildinfo
```

Этот файл не должен оставаться в проекте после завершения работы.

### Запрещено генерировать ключи подписи

Агенту **нельзя** запускать `npx tauri signer generate` и создавать ключи
подписи обновлений — ни во временном каталоге, ни в репозитории, ни где-либо
ещё. Это касается и «пробной» генерации для проверки.

Причина: приватный ключ, попавший не туда, ломает выпуск обновлений, а
сгенерированную пару легко потерять — восстановить её нечем. Уже выпущенные
приложения проверяют подпись тем публичным ключом, который вшит в
`src-tauri/tauri.conf.json` (`plugins.updater.pubkey`), поэтому новый ключ без
решения мейнтейнера сделает все предыдущие релизы непроверяемыми.

Вместо генерации:

* проверять согласованность пары **подписью тестового файла**, а не сравнением
  префиксов;
* если ключи не согласуются — сообщить об этом и спросить пользователя.

**Как проверять согласованность правильно.** В minisign публичный ключ и
подпись **разделяют первые 10 байт** — это алгоритм (2 байта, `RW` против `RU`)
и `key_id` (8 байт). Дальше идут разные данные: у публичного ключа — сам ключ,
у подписи — подпись. Поэтому:

* `sign.startsWith(pubkey)` **всегда даёт false**, даже для верной пары —
  сравнивать так нельзя;
* сравнивать нужно только `key_id`: 10 символов base64 после двухсимвольного
  алгоритма.

```text
алгоритм + key_id = первые 12 символов строки
pubkey : RW QuHHLci5yT5…
подпись: RU QuHHLci5yT5…   ← key_id совпадает, пара согласована
```

Различаются также и форматы файлов: `updater.key` начинается с `RWRT`
(зашифрованный приватный ключ), а `updater.key.pub` и подписи — с `RW`/`RU`.
Их префиксы нельзя сравнивать между собой.

Файлы ключей лежат в `.tauri/` и исключены из Git. Приватный ключ и пароль
нельзя выводить в чат, коммиты или логи.

## 8. Безопасность существующего функционала

При изменении кода:

* не ломай существующий функционал;
* не удаляй рабочий код без необходимости;
* не меняй поведение компонентов, не связанных с задачей;
* не меняй UI/UX без необходимости;
* не выполняй "улучшения" вне scope задачи;
* не делай массовый рефакторинг ради рефакторинга.

Если задача требует рефакторинга, поведение приложения до и после рефакторинга должно оставаться эквивалентным, если пользователь явно не попросил изменить поведение.

## 9. Перед завершением задачи

Перед тем как сообщить пользователю о завершении:

1. Проверь изменённые файлы.
2. Убедись, что требования задачи выполнены.
3. Запусти `cargo build`, `tsc --noEmit` и `npm run lint`. Тесты **не**
   запускай — см. раздел 10.
4. Проверь, что не появился `tsconfig.node.tsbuildinfo`.
5. Проверь, что `lineHeight === 1`.
6. Проверь, что `releaseType === "draft"`.
7. Проверь, что `favorites: SSHConfig[]` находится последним в `AppConfig`.
8. Если менялась версия — проверь, что все **шесть** мест совпадают (раздел 5),
   а `tauri.conf.json` остался без BOM.
9. Убедись, что новые UI-тексты имеют RU/EN локализацию.
10. Убедись, что не появились `any`/`unknown` без необходимости.
11. Не сообщай о завершении, если сборка или проверка выявила очевидную проблему — сначала исправь её.

## 10. Тесты запускать нельзя

### Правило

Агенту **запрещено** запускать `cargo test` и `npm test` в этом проекте.

```bash
# НЕ выполнять:
cargo test
cargo test --manifest-path src-tauri/Cargo.toml
npm test
```

Проверка изменения выполняется **компиляцией и типами**:

```bash
cargo build --manifest-path src-tauri/Cargo.toml
npx tsc --noEmit -p tsconfig.json
npm run lint
node scripts/gen-updater-config.mjs
```

### Почему

`npm test` в `package.json` вызывает `cargo test`, поэтому обе команды дают
один и тот же сбой. Тест-бинарь на Windows не стартует:

```text
error: test failed, to rerun pass `--lib`
process didn't exit successfully: ... (exit code: 0xc0000139, STATUS_ENTRYPOINT_NOT_FOUND)
```

Причина — цепочка зависимостей:

```text
yassh-client (feature "default")
  → tauri feature "default"
    → tauri feature "common-controls-v6"
      → muda feature "common-controls-v6"
        → импорт comctl32.dll :: TaskDialogIndirect
```

`TaskDialogIndirect` есть только в **Common Controls v6**. Загрузчик берёт
`comctl32` из `WinSxS` сборки **5.82**, где этого экспорта нет. `cargo build`
проходит: линковщик берёт функции из `comctl32.lib`, а несоответствие
обнаруживается только при загрузке процесса — то есть исключительно на тестах.

Проверено и опровергнуто: копирование `comctl32.dll` v6 рядом с бинарём не
помогает — библиотека подхватывается через SxS-активацию, локальная копия не
участвует. Исправление затрагивает сборочную конфигурацию, а не код, и решается
мейнтейнером отдельно.

### Чего не делать

* **Не запускать** `cargo test` в попытке «а вдруг теперь работает» — время
  тратится впустую, результат не изменится;
* **не чинить** это самостоятельно: правки в `build.rs`, `Cargo.toml` и
  `.tauri/` выходят за рамки задачи и требуют решения мейнтейнера;
* **не считать** провал тестов своей ошибкой и не выдавать его за успех;
* **не писать** в отчёте «тесты прошли», если они не запускались.

### Что писать в отчёте

Указывай честно: проверка выполнена компиляцией, типами и линтером; тесты не
запускались из-за известного сбоя окружения (см. «Почему»). Не выдавай сбой
окружения за свою ошибку — и не наоборот.

## Главное правило

**Не меняй то, о чём пользователь не просил.**

Не выполняй дополнительные рефакторинги, изменения дизайна, обновления зависимостей, изменения архитектуры или "улучшения" вне текущей задачи без явной необходимости.
