# Инструкции для AI-агентов

Эти правила обязательны для всех AI-агентов, работающих с проектом.  
Если задача пользователя противоречит этим правилам, приоритет имеют эти инструкции, если пользователь явно не переопределил конкретное правило в текущей сессии.

---

## 1. Терминал (Terminal)

### `lineHeight`
- В `src/components/Terminal.tsx` параметр `lineHeight` **ВСЕГДА** должен иметь значение `1`.
- Запрещено устанавливать `1.1`, `1.2` или любое другое значение.
- Изменение разрешено **только если пользователь явно попросил изменить `lineHeight` в текущей сессии**.
- Не изменяй `lineHeight` косвенно через другие настройки или стили.

### Инициализация терминала
При инициализации терминала обязательно соблюдать правильный pipeline:

1. Создать и инициализировать терминал.
2. Подключить addons.
3. Выполнить `fitAddon.fit()`.
4. Только после этого устанавливать SSH-соединение.

`fitAddon.fit()` должен выполняться **до установки SSH-соединения**.

## 2. Стили и шрифты (Styles & Fonts)

### Пути к шрифтам
В CSS при использовании `@font-face`:

- Запрещено использовать пути с префиксом `./`.
- Использовать пути, начинающиеся непосредственно с директории.

Правильно:

`csssrc: url('/fonts/FontName.woff2');`

Запрещено:

`src: url('./fonts/FontName.woff2');`

Это необходимо для корректной работы ассетов в production-сборке Electron.

### Шрифты проекта

* **Никогда не удаляй файлы из `public/fonts/`.**
* **Никогда не удаляй существующие `@font-face`.**
* Все шрифты, перечисленные в `src/hooks/useSystemFonts.ts`, должны:

  * физически присутствовать в проекте;
  * быть зарегистрированы через `@font-face`;
  * корректно использоваться приложением.
* Не заменяй проектные шрифты системным fallback.
* Особенно важно не допускать fallback на `serif`.

### Иконки

* `./icons/icon48.png` в `TitleBar` должен сохранять существующий стиль.
* `./icons/icon256.png` в `SettingsView` должен сохранять существующий стиль.
* Не заменяй эти иконки без явного указания пользователя.
* Не изменяй их визуальный стиль в рамках рефакторинга или оптимизации.

## 3. Код и типизация (Code & Typing)

Проект использует строгую типизацию TypeScript.

### Запрещено

Без крайней необходимости запрещено использовать:

TypeScript: `any/unknown`

Предпочитай:

* конкретные типы;
* существующие типы проекта;
* generic-типы;
* type guards;
* discriminated unions.

Не ослабляй типизацию только для того, чтобы быстрее исправить ошибку компиляции.

### Важное правило

Не переписывай рабочую типизацию на `any` или `unknown` для устранения ошибок после рефакторинга.

## 4. Локализация (Localization)

### Общение

* Все сообщения AI-агента пользователю должны быть **на русском языке**.

### UI приложения

Все пользовательские тексты в UI должны поддерживать:

* 🇷🇺 русский;
* 🇬🇧 английский.

Новые:

* кнопки;
* сообщения;
* уведомления;
* ошибки;
* tooltips;
* labels;
* настройки;
* заголовки

должны добавляться сразу на оба языка через существующую систему локализации проекта.

### PR и коммиты

* PR должны быть составлены **на русском языке**.
* Описания коммитов должны быть **на русском языке**.

## 5. Версионирование (Versioning)

Если пользователь **явно не указал версию**, которую необходимо установить:

* увеличивать версию только на `+0.0.1` за одну сессию.

Пример:

```text
1.8.1 → 1.8.2
```

После `.9` переносить разряд:

```text
1.8.9 → 1.9.0
1.9.9 → 2.0.0
```

При изменении версии обязательно синхронно обновлять:

```text
package.json
package-lock.json
src/types.ts
```

Не изменяй версию в других файлах без необходимости.

### `releaseType`

В `package.json`:

`"releaseType": "draft"`

должно оставаться **всегда**.

Запрещено менять:

```text
draft → release
```

или на любое другое значение.

Не изменяй `releaseType`, даже если считаешь, что это необходимо для автообновлений или публикации.

После выполнения задачи удаляй генерируемый мусор, если он появился в результате работы агента.

В частности:

```text
tsconfig.node.tsbuildinfo
```

Этот файл не должен оставаться в проекте после завершения работы.

## 8. Безопасность существующего функционала

При изменении кода:

* не ломай существующий функционал;
* не удаляй рабочий код без необходимости;
* не меняй поведение компонентов, не связанных с задачей;
* не меняй UI/UX без необходимости;
* не выполняй "улучшения" вне scope задачи;
* не делай массовый рефакторинг ради рефакторинга.

Если задача требует рефакторинга, поведение приложения до и после рефакторинга должно оставаться эквивалентным, если пользователь явно не попросил изменить поведение.

## 10. `cargo test` на Windows: обязательная подготовка

### Симптом

```text
error: test failed, to rerun pass `--lib`
process didn't exit successfully: ... (exit code: 0xc0000139, STATUS_ENTRYPOINT_NOT_FOUND)
```

Ошибка **не связана с кодом проекта и не с правками агента**: она возникает на
чистом дереве при `git stash`, то есть задокументированное поведение окружения.

### Причина

Цепочка зависимостей:

```text
yassh-client (feature "default")
  → tauri feature "default"
    → tauri feature "common-controls-v6"
      → muda feature "common-controls-v6"
        → импорт comctl32.dll :: TaskDialogIndirect
```

`TaskDialogIndirect` существует только в **Common Controls v6**
(`Microsoft.Windows.Common-Controls`, версия `6.0.0.0`). Проверено на этой
машине: в `C:\Windows\System32\comctl32.dll` этого экспорта нет (там v5,
119 экспортов), а загрузчик при отсутствии манифеста подхватывает из
`WinSxS` сборку **5.82**, где `TaskDialogIndirect` тоже отсутствует —
проверено вызовом `LoadLibrary("comctl32.dll")` с выводом пути.

`cargo build` при этом проходит успешно: линковщик берёт функции из
`comctl32.lib`, а несоответствие обнаруживается только при загрузке
процесса. Поэтому ошибка возникает исключительно на `cargo test`.

### Что НЕ работает

**Копировать `comctl32.dll` v6 рядом с бинарём — бесполезно.**
Проверено: копия из
`C:\Windows\WinSxS\amd64_microsoft.windows.common-controls_*_6.0.*`
лежит в `target/debug/deps/`, экспорт в ней есть, `LoadLibrary` этого файла
успешно возвращает `TaskDialogIndirect` — но тест-бинарь всё равно падает.
Причина в том, что `comctl32` подхватывается через SxS-активацию из
`WinSxS`, и локальная копия не участвует. `comctl32.dll` при этом **не**
входит в `KnownDLLs`, так что дело именно в SxS-манифесте, а не в поиске DLL.

### Что работает

Нужен манифест с объявленной зависимостью от v6. Проверено на минимальном
репро: бинарь с `comctl32::TaskDialogIndirect` **без** манифеста падает с
`0xC0000139`, **с** манифестом — запускается.

Манифест должен содержать:

```xml
<?xml version="1.0" encoding="UTF-8" standalone="yes"?>
<assembly xmlns="urn:schemas-microsoft-com:asm.v1" manifestVersion="1.0">
  <assemblyIdentity type="win32" name="yassh_client_lib" version="4.0.0.0"/>
  <dependency>
    <dependentAssembly>
      <assemblyIdentity
        type="win32"
        name="Microsoft.Windows.Common-Controls"
        version="6.0.0.0"
        processorArchitecture="*"
        publicKeyToken="6595b64144ccf1df"
        language="*"/>
    </dependentAssembly>
  </dependency>
</assembly>
```

Текущий манифест тест-бинаря содержит только `trustInfo` и `compatibility` —
блока `<dependency>` в нём нет, поэтому активация v6 и не происходит.

### Порядок действий агента

1. **Запусти `cargo test` и убедись в падении.** Если тесты идут — этот
   раздел не нужен.
2. **Не трать время на копирование `comctl32.dll`** — см. «Что НЕ работает».
3. **Спроси у пользователя**, прежде чем что-то менять: правка затрагивает
   сборочную конфигурацию, а не код приложения. Возможные пути:
   * встроить манифест в тест-бинарь через `build.rs` (нужен `rc.exe` из
     Windows SDK; в MSYS2 его заменяет `windres`);
   * отключить фичу `common-controls-v6` у `tauri` (требует правки
     `Cargo.toml` и может повлиять на поведение UI);
   * запускать тесты на другой машине / в CI-образе с установленным SDK.
4. **Не объявляй задачу готовой**, пока `cargo test` фактически не проходит.
   Проверка компиляцией (`cargo build`) и типами **не заменяет** прогон тестов.
5. Если тесты запустить не удалось — честно сообщи об этом пользователю и
   укажи причину (см. «Причина»), не выдавая сбой окружения за свою ошибку
   и не наоборот.

### Диагностика без GUI-инструментов

Windows SDK (`dumpbin.exe`, `mt.exe`) в этом окружении **отсутствует**.
Проверять импорты и экспорты PE приходится собственными средствами;
`cargo test` для этого не нужен. Полезно помнить:

* ошибка `0xC0000139` = DLL найдена, но нужного экспорта в ней нет
  (в отличие от `0xC0000135` «DLL не найдена»);
* `GetModuleFileNameA` после `LoadLibrary("имя.dll")` показывает, какую
  реально сборку выбрал загрузчик — самый быстрый способ увидеть
  подмену на WinSxS.

## Главное правило

**Не меняй то, о чём пользователь не просил.**

Не выполняй дополнительные рефакторинги, изменения дизайна, обновления зависимостей, изменения архитектуры или "улучшения" вне текущей задачи без явной необходимости.
